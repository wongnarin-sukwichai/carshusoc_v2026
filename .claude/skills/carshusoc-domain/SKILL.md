# CARS-HUSOC domain reference

This is the long-form reference `CLAUDE.md` points to. The spec this was extracted from lives at `docs/exampage-mockup-reference.jsx` — a React JSX mockup the client supplied (not real code, not routed). Re-read it directly if a rule below seems ambiguous; this file is a summary, not a replacement.

## The three service centers

Each center's visibility is toggled via the `service_centers` table (`code`: `training` | `exam` | `translation`, `is_visible`). A hidden center disappears from both the public landing page (`Welcome.vue`) and the user sidebar (`UserSidebar.vue`) — gated by a `serviceCenters` prop (keyed by `code` → `is_visible`) shared globally via `HandleInertiaRequests`. The **admin** sidebar/routes are intentionally left unfiltered — an admin needs to reach a center's management pages precisely to work on it while it's hidden from the public.

### 1. Training center (`courses`, `course_enrollments`)

- A course has a `prerequisite_course_id` (self-referencing FK). A user may only enroll in a course if their enrollment status for the prerequisite is `passed`. The mockup's `checkCourseEligibility()` is the reference implementation of this rule (locks the button, shows the reason).
- Enrollment lifecycle: `pending_payment` → (slip approved) → `studying` → (admin grades) → `passed` | `failed`. A `failed` enrollment should let the user retry (mockup doesn't handle this explicitly — decide when building).
- `courses.requires_receipt` — per-course toggle for whether a receipt is needed on payment (req 4.8, generalized to exams too).
- `courses.location` — where the training happens (req 4.6). Changing it should email everyone currently enrolled (any status) using the `location_changed` email template (req 4.7) — not yet wired to any observer/event.

### 2. Exam center (`exams`, `exam_registrations`, `score_scales`, `score_scale_bands`)

- Score entry is 4 components, each out of 25: `listening_score`, `reading_score`, `conversation_score`, `grammar_score` → `total_score` out of 100 (see `docs/score.png` layout referenced in the original request — a MSU-EPT score report table). Import is per-person or CSV (`email,score` in the mockup's simplified single-score version — the real version needs all 4 components per row).
- **Score → CEFR lookup must be versioned.** `score_scales` has a `version`/`effective_from`; `score_scale_bands` holds the actual TOEIC/CEFR/EPT range table (the comparison table image from the request). When scoring a registration, snapshot the `score_scale_id` actually used onto `exam_registrations.score_scale_id` (and again onto `certificates.score_scale_id` when the certificate is issued). **Never re-derive CEFR from the exam's *current* `score_scale_id` for a historical registration** — that's the whole reason the scale is versioned (req 4.2: a future rescale must not silently change someone's already-issued certificate).
- `mail_delivery_available` / `mail_delivery_fee` on `exams`, `wants_mail_delivery` / `mail_delivery_fee_charged` on `exam_registrations` — the "ส่งผลสอบทางไปรษณีย์" option (req 4.1.6). Fee is admin-configurable per exam round (`admin/CoursesExams.vue`). The user-facing checkout is built too: the opt-in checkbox lives in `PaymentSlipDialog.vue` (not at the instant "register" click — mirrors the existing `wants_receipt` checkbox), shown only when `payableType === 'exam_registration'` and the exam has `mail_delivery_available`. `User\PaymentController::store()` adds the fee to the charged `amount` and snapshots `wants_mail_delivery`/`mail_delivery_fee_charged` onto the `ExamRegistration` — never re-derive from the exam's live fee later. `admin/Payments.vue` shows the fee per row, same pattern as the receipt column.
- `exams.location` — same location-change-email rule as courses (req 4.6/4.7), scoped to everyone registered for that exam round.

### 3. Translation center (`translation_requests`) — built

- Lifecycle: `submitted` (user uploads source doc, `User\TranslationRequestController@store`, private disk) → (admin sends quote: `estimated_price` + `delivery_date`, `Admin\TranslationRequestController@quote`) → `quote_sent` → (payment approved via the shared `Payment` flow, see below) → `translating` → (admin uploads result, `Admin\TranslationRequestController@deliver`, public disk) → `completed` → user downloads via `User\TranslationRequestController@download` (403s unless it's their own request).
- No prerequisite/eligibility logic here, unlike training.
- `translation_request` is registered in the morph map and is a third case everywhere the `payable_type` polymorphism is handled — `User\PaymentController::ALLOWED_TYPES`/`AWAITING_PAYMENT_STATUS` (its "awaiting payment" status is `quote_sent`, not `pending_payment` like courses/exams — that's the one place the three payable types genuinely diverge), `Admin\PaymentController::approve()`/`labelFor()`, `PaymentSlipDialog.vue`'s `payableType` prop union.
- See `tests/Feature/TranslationCenterTest.php` for the full pipeline exercised end-to-end in one test (submit → quote → pay → approve → deliver → download, plus a cross-user 403 check).

## Payments (`payments`, polymorphic via `payable_type`/`payable_id`)

Every payable thing (`CourseEnrollment`, `ExamRegistration`, `TranslationRequest`) gets a `Payment` row when the user attaches a slip. Admin approves/rejects. Approving a payment is what should flip the parent record's status (`pending_payment` → `studying`/`registered`/`translating`) — see the mockup's `adminApprovePayment()` for the three branches. `wants_receipt` mirrors the payable's `requires_receipt` flag at the time of payment (snapshot, don't just read the course/exam live).

## Certificates (`certificates`, `certificate_templates`)

- One `certificate_templates` row per design, scoped by `service_center_code`. Admin can have multiple templates per center and upload a different `background_image_path` per template (req 4.5) — training certs and exam certs look different (see `docs/cert-*.png`-style layouts referenced in the original request: exam center has a 3-signature score-table layout, training center has a 2-signature "ประกาศนียบัตร" layout).
- When a certificate is actually issued, create a `certificates` row that **snapshots** `certificate_template_id` and (for exam certs) `score_scale_id` — this is what makes req 4.2 ("ผู้ใช้กลับมาโหลดใบเซอร์เดิมได้แม้เกณฑ์เปลี่ยนไปแล้ว") work: the download endpoint should always render from the certificate's own snapshotted template/scale, never from the course/exam's *current* template.
- `verification_hash` powers a public "verify this certificate" lookup page: `GET /certificates/verify/{certificate:verification_hash}` (route-model-bound on that column, so a bad hash 404s automatically — no policy/`firstOrFail()` needed) → `App\Http\Controllers\CertificateVerificationController@show` → `resources/js/pages/CertificateVerify.vue`. Top-level controller (not under `User`/`Admin`) since it's neither-guard public. Shows recipient name, item name, issue date, and — for exam certs — the `total_score`/`cefr_level` already snapshotted directly on the `ExamRegistration` row (no need to touch `score_scale_id` for display, that's only for re-deriving CEFR bands). Not built: embedding the verify URL/QR into the certificate PDF blade templates.

## Email (`email_templates`, `email_logs`)

Known template keys used by the mockup's flows: `welcome`, `payment_approved`, `score_released`. This build adds `location_changed` (req 4.7), `translation_quote_sent`, `translation_delivered` for the two lifecycles above. `email_logs` is an audit trail (`related_type`/`related_id` morphs to whatever triggered the email) — the mockup's sidebar "live log" panel reads from something equivalent to this.

## Admin roles — permission gating built

`admins.role` enum: `admin`, `staff` — simplified from an original 4-value enum (`super_admin`, `translation_manager`, `finance_officer`, `staff`) by explicit user decision, since the middle two operational roles were always equal in practice anyway. Permission gating is **two-tier**, not a full per-role matrix: `admin` reaches everything; `staff` shares every page *except* three reserved for `admin` — Staff (`admin.staff`), Email Templates (`admin.email-templates`), and Certificate Templates (`admin.certificate-templates`/`.update`). Day-to-day operational pages (payments, registrants, courses-exams, exam-scores, course-grading, translation-quotes, manual, dashboard) are open to any authenticated admin regardless of role.

Enforcement: `App\Http\Middleware\EnsureAdminHasRole` (aliased `admin.role` in `bootstrap/app.php`), applied as `Route::middleware('admin.role:admin')->group(...)` around the three reserved routes in `routes/admin.php` — takes a variadic role list so it generalizes if finer-grained roles are ever needed (`admin.role:admin,someOtherRole` etc.). `AdminSidebar.vue` mirrors this by hiding those three nav items for non-`admin` roles (`adminOnly` flag on the nav item + `isAdmin` computed from `page.props.auth.admin.role`) — that's UX only, not the real gate. See `tests/Feature/AdminRolePermissionTest.php`.

The DB-level rename from the 4-value enum happened via a data-safe migration (`2026_07_21_100000_simplify_admin_roles.php`) — widens the enum, remaps `super_admin`→`admin` and `translation_manager`/`finance_officer`→`staff`, then narrows to the final 2 values. If a fuller per-role matrix is ever wanted again later (e.g. a role scoped to payments-only), the variadic `admin.role:...` middleware already supports it — it'd just need new role values reintroduced and a routes/admin.php + sidebar change.

## What's built vs. not

**Built (foundation pass):** every table as a migration + Eloquent model with relationships. `admin`/`web` guard split. Seeders (`AdminSeeder`, `ServiceCenterSeeder`). Routes + pages for every screen in the mockup, wrapped in role-specific sidebars.

**Built (payment/scoring/certificate pass):**
- User: `user/Training.vue` + `user/Exam.vue` list visible courses/exams and let the user enroll/register (`User\CourseEnrollmentController`, `User\ExamRegistrationController` — prerequisite/eligibility re-checked server-side, mirrors the mockup's `checkCourseEligibility()`) and upload a slip via `components/PaymentSlipDialog.vue` → `User\PaymentController@store`. Slips are stored on the **private** disk (`storage/app/private/slips/{user_id}/...`), not public — they're financial evidence.
- Admin: `admin/Payments.vue` — approve/reject queue (`Admin\PaymentController`), approving flips the enrollment/registration status (`studying`/`registered`).
- Admin: `admin/ExamScores.vue` — per-exam registrant table with manual score entry (4 components) and CSV import (`email,listening,reading,conversation,grammar`), both routed through `Admin\ExamScoreController@applyScore()` which resolves CEFR via `ScoreScale::resolveBand()` and snapshots the scale used.
- Admin: `admin/CourseGrading.vue` — per-course enrollment table, pass/fail (`Admin\CourseGradingController`).
- Admin: `admin/CertificateTemplates.vue` — edit the two seeded templates' text/signatories/border color (`Admin\CertificateTemplateController`; no create/delete — see below).
- Certificate PDF issuance is real: `App\Services\CertificateIssuer` renders `resources/views/certificates/{training,exam}.blade.php` via dompdf to `storage/app/public/certificates/`, `updateOrCreate`s the `Certificate` row (snapshotting template + score scale). Triggered automatically when a course enrollment is marked `passed` or an exam registration is scored. User downloads from `user/Portfolio.vue` → `User\CertificateController@download` (403s unless it's their own certificate).
- Polymorphic columns (`payments.payable_type`, `certificates.certifiable_type`, `email_logs.related_type`) use a Laravel morph map (`AppServiceProvider::boot()`) with short aliases (`course_enrollment`, `exam_registration`, `translation_request`) instead of raw class names — always build these relations via `$model->getMorphClass()`, never `Model::class`, or the stored alias will be inconsistent.
- `DemoContentSeeder` seeds 2 courses, 1 exam, the score scale, and both certificate templates — no longer the only way to get data in, just a convenience for a fresh `migrate:fresh --seed`.
- Admin: `admin/CoursesExams.vue` — full course/exam CRUD (`Admin\CourseController`, `Admin\ExamController`, listed via `Admin\CourseExamController@index`). One form per resource, reused for both create and edit (tracked by a local `editingCourseId`/`editingExamId` ref — `null` means create-mode, posts to `.store`; set means edit-mode, puts to `.update`). Server-side validation blocks duplicate `code` and a course being its own `prerequisite_course_id` (`Rule::notIn`) — see `tests/Feature/CourseExamManagementTest.php`. Show/hide is a separate lightweight `PATCH .../toggle-visibility` action, not part of the edit form.

**Built (translation center pass):** the full `translation_requests` lifecycle described above — `user/Translation.vue` (submit + history + pay), `admin/TranslationQuotes.vue` (view source doc, send quote, deliver result).

**Built (certificate template CRUD pass):** `admin/CertificateTemplates.vue` supports create/delete, not just edit — a service center can now have more than one template (e.g. a seasonal design). The invariant `App\Http\Controllers\Admin\CertificateTemplateController` enforces: **exactly one `is_default` template per `service_center_code`, always** (never zero, since `CertificateIssuer::defaultTemplateFor()` does a `firstOrFail()` on it).
- `store()`: if the new template is the first one for its center, it's force-defaulted regardless of what was submitted (`ensureSingleDefault()`). If submitted as default, every sibling in that center is un-defaulted.
- `update()`: unchecking "default" on the current sole default throws a `ValidationException` (`is_default` field) — that's a normal form validation error, surfaces via `form.errors.is_default` like any other.
- `destroy()`: refuses (via `back()->with('error', ...)`, not an exception) to delete a template that (a) has any `certificates` referencing it — historical PDFs must keep resolving their snapshot — or (b) is the last template for its center. Deleting a non-last default auto-promotes the oldest remaining sibling to default.
- Scoped to `training`/`exam` only (`CertificateTemplateController::CENTER_CODES`) — translation delivers a document, not a certificate, so it was deliberately left out of the center-code dropdown.
- See `tests/Feature/CertificateTemplateManagementTest.php` for all the invariant edge cases exercised directly (this is exactly the kind of app-level constraint that's easy to get wrong silently, so re-run these if you touch this controller).

**Built (i18n + SweetAlert2 pass, later extended to full coverage):** the original pass limited scope to infrastructure + shared chrome; a later pass extended `$t()`/`useI18n()` to every user/admin page's actual content, plus controller-generated flash messages, closing that gap.

- `vue-i18n` (Composition API, `legacy: false`) set up in `resources/js/lib/i18n.ts`, messages in `resources/js/lang/{th,en}.ts`, registered in `app.ts` via `.use(i18n)`. Locale persists in a `locale` cookie (1 year), read on boot by `readLocaleCookie()` — **not** synced to the Laravel session/backend locale at all; this stays a pure frontend concern, including for the flash-message translation below.
- `resources/js/composables/useLocale.ts` exposes a `locale` ref (get/set, writes the cookie) and `toggle()`. `components/LocaleSwitcher.vue` is the UI (a two-state toggle button, not a dropdown — there are only 2 locales), wired into `AppSidebarHeader.vue` (every authenticated user/admin page), and also placed directly in `Welcome.vue`'s header since that page isn't wrapped in either sidebar layout.
- Translated: `common.*`, `nav.user.*`/`nav.admin.*`, `app.*`, plus every page namespace (`user.*`, `admin.*`, `components.*`, `welcome.*`, `certificateVerify.*`) and a `flash.*` namespace for controller messages.
- **Controller flash messages**: since the backend doesn't know the user's locale (it's a frontend-only cookie), `back()->with('status'/'error', ...)` now flashes `['key' => 'flash.xxx.yyy', 'params' => [...]]` instead of a raw string — Laravel session flash accepts arrays, Inertia passes them through as-is. `components/FlashMessage.vue` resolves the key via `useI18n()`'s `t()` before toasting; a plain string still works as a fallback (untouched call sites, e.g. `Auth/*` controllers). This covers `User\*`/`Admin\*` controllers only — `app/Http/Controllers/Auth/*` (starter-kit flows) and `abort_if(..., 422, '...')` calls (different render path, not the flash+toast system) were deliberately left alone.
- `Welcome.vue` was rewritten with real CARS-HUSOC content (service center cards, sourced from the same `is_visible`-filtered `centers` the `/` route now passes) and given `$t()` + a `LocaleSwitcher` from the start.
- If asked to extend i18n coverage to new content: add keys to both `lang/th.ts` and `lang/en.ts` under a namespace matching the page/concern (e.g. `admin.payments.*`, `flash.someController.*`), then either `useI18n()` in `<script setup>` for anything needing reactivity in computed data, or `$t()` directly in the template.

**Built (SweetAlert2 pass):**
- `resources/js/lib/swal.ts` — `confirmDialog({ title, text?, icon? }): Promise<boolean>` (replaces native `confirm()`, Tailwind-styled buttons via `buttonsStyling: false` + `customClass`) and `successToast(message)`/`errorToast(message)` (bottom-end toasts, 4.5s).
- **Fixed an app-wide bug while wiring this up**: `HandleInertiaRequests` never shared session flash data to the frontend, so every controller's `back()->with('status', ...)` across the whole app (built over several prior passes — payments, grading, templates, everything) was silently invisible. Fixed by sharing `flash.status`/`flash.error` (`Inertia::always(...)` so it's never dropped by partial reloads) and rewriting `components/FlashMessage.vue` from a custom banner into a side-effect-only component (`<template></template>`) that watches `page.props.flash` and calls `successToast`/`errorToast`. Still mounted once, globally, via `AppShell.vue`. New controller code: `->with('status', ...)` for success, `->with('error', ...)` for user-facing non-validation failures (validation errors still go through the normal `ValidationException` → `form.errors` path, untouched by this).
- The one pre-existing native `confirm()` in the codebase (`admin/CertificateTemplates.vue`'s delete button) was migrated to `confirmDialog()`. No other confirmations were added — this pass replaced what existed, it didn't audit the app for actions that arguably *should* have a confirmation but never had one (e.g. reject payment, fail a course enrollment).
- `sweetalert2/dist/sweetalert2.min.css` is imported at the very top of `resources/css/app.css` (before the `@tailwind` directives — CSS `@import` must precede everything else or PostCSS warns), plus a few `.swal2-popup`/`.swal2-title` overrides so popups pick up the app's light/dark card color tokens instead of shipping SweetAlert2's default white popup.

**Not built — needs real implementation, one flow at a time:**
- Location-change → bulk email notification (courses/exams have a `location` column; nothing watches for changes yet)
- Email template admin CRUD + actual mail sending (`email_templates` table exists but nothing sends)
- MSU SSO/OAuth login (`users.auth_provider`/`sso_subject` columns exist; no client wired — needs the university's endpoint/client credentials first)
- Embedding the certificate verify URL/QR into the certificate PDF blade templates (the verify page itself is built — see Certificates section — this is just about making it discoverable from the PDF)
- Anuphan font (still not added, per `CLAUDE.md`)

Prerequisite cycle detection (`Admin\CourseController::wouldCreateCycle()`), mail-delivery fee checkout, service-center visibility gating, the public certificate verify page, full-page i18n + flash-message translation, and the 2-role admin scheme are all now built — see their respective sections above rather than treating them as gaps.

When picking up one of these, re-check the relevant section above against `docs/exampage-mockup-reference.jsx` for the exact interaction details (button states, validation messages, etc.) before implementing. `tests/Feature/ServiceCenterPagesTest.php` has the pattern for testing across both guards (`actingAs($user, 'web')` vs `actingAs($admin, 'admin')`).
